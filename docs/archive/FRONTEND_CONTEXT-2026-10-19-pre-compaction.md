# Frontend Project Context

This document records the repository state as inspected on 2026-10-10, updated through FEATURE-009, the planner trail-dataset change, viewport-driven Discover (2026-10-17), FEATURE-010 (2026-10-18), and FEATURE-011 (PASS, frozen 2026-10-19; the first feature of the approved FEATURE-011 to FEATURE-014 extension, PRD section 1.1; FEATURE-012 is next). ## 1. Product Overview

The Outdoor Trip Companion is a web application organized around the product journey **Discover → Plan → Prepare → Go in real life → Remember** (`docs/PRODUCT_REQUIREMENTS.md` sections 2 and 5). The intended journey is: discover real trails publicly, sign in, describe a hike in natural language or choose a discovered trail, receive trail recommendations based on preferences, trail data, weather, proximity, and owned gear, select a trail and date, receive a packing recommendation, maintain owned gear, equip gear for the trip on a real-time 3D avatar, go on the real trip, and later keep memories. (Earlier documents used the working stages Plan → Pack → Explore → Memory; the outdoor scene and Explore stage were removed on 2026-10-14.)

CURRENT backend coverage is strongest for Plan and Pack. FEATURE-005 (PASS, frozen 2026-10-14) made the Gear Customization Studio and its real-time 3D avatar, which shows equipped gear, part of the current frontend baseline. FEATURE-006 (PASS, frozen 2026-10-15) made the signed-out homepage at `/` a two-stage page: the FEATURE-001 cinematic Hero, then Discover (trail map, synchronized list, map-anchored trail popup, Daily Trail Activity), served by public trail reads (section 4). Its approved post-freeze evolution, viewport-driven Discover (PASS / FROZEN 2026-10-17; no new feature number), reads the trails of the current map area from the public `GET /api/trails/nearby` and clusters them MapLibre-natively (section 8). FEATURE-007 (PASS, frozen 2026-10-16) made `/gear` My Gear: the signed-in user's owned-gear collection with add, edit, and remove, the same inventory the Gear Studio reads, while the Studio stays trip-specific. FEATURE-008 (PASS, frozen 2026-10-16) added the Memory backend: a new `memory-service` with owner and public Memory APIs and private photo storage (sections 3 and 4). FEATURE-008 has no user interface of its own. FEATURE-009 (PASS, frozen 2026-10-17) added My Memories at `/memories`: the signed-in user's journal of trips with Memory Detail, a shared Create/Edit editor, photo upload, ordering and removal, and a per-Memory Private or Public choice, using only the owner APIs (sections 4, 7, 8). FEATURE-010 (PASS, frozen 2026-10-18) added Community Memories in Discover: the selected curated trail's popup previews its PUBLIC Memories, and a docked Community panel lists them and opens one read-only, all through FEATURE-008's tokenless public Memory API with no backend change (sections 4, 7, 8). It is the last feature; the product is in its feature freeze. The outdoor Adventure scene and the 3D Explore stage were removed from the product on 2026-10-14.

The intended visual direction is a modern, clean, cinematic outdoor product. It should not resemble a generic enterprise dashboard or a purple-gradient AI SaaS template. Anime-inspired or stylized 3D elements may be added later but are outside the first frontend slice.

Product source: `DocumentsAndReports/JiayuL_Proposal.md`.

| `trail-service` | 8082 | Trail search, PostGIS nearby search, detail/GeoJSON response, scenery, and baseline gear requirements | CURRENT, usable with prototype data |
| `recommendation-service` | 8083 | OpenAI intent extraction, trail/user service orchestration, Open-Meteo lookup, scoring, and packing recommendations | CURRENT; primary query works, with integration risks below |

Infrastructure in `Project/docker-compose.yml` starts PostGIS/PostgreSQL and Keycloak 26.7.4. `Project/docker/postgres/init-databases.sql` creates `user_db`, `trail_db`, and (from FEATURE-008) `memory_db`; Keycloak uses the database named by `POSTGRES_DB`. The compose file does not start the Spring services.

Databases:

- `user_db`: `users` and `gear_items`, managed by Flyway in `Project/Backend/user-service/src/main/resources/db/migration/`.
- `trail_db`: PostGIS `trails`, `trail_scenery`, and `trail_gear_requirements`, managed by Flyway in `Project/Backend/trail-service/src/main/resources/db/migration/`.
- `memory_db` (FEATURE-008): `memories` and `memory_photos`, managed by Flyway in `Project/Backend/memory-service/src/main/resources/db/migration/`. No PostGIS, and no foreign key to any other database. The init script runs only when the Postgres volume is first created, so a volume created before FEATURE-008 needs a one-time `CREATE DATABASE memory_db;` (`CLAUDE.md`, Commands). Never delete the volume to get it.
- `plan_db` (FEATURE-011): `plans`, managed by Flyway in `Project/Backend/plan-service/src/main/resources/db/migration/`; partial unique index `uk_plans_owner_trail_date_active (owner_subject, trail_id, trip_date) WHERE deleted = FALSE`. No foreign key to any other database. As for `memory_db`, a volume created before FEATURE-011 needs a one-time `CREATE DATABASE plan_db;` (done on the development volume 2026-10-19). Never delete the volume to get it.
- The recommendation service has no database; it orchestrates other services and external APIs.

External integrations:

- Keycloak issuer: `http://localhost:8180/realms/outdoor-trip`.
- OpenAI Java SDK: structured intent extraction; client is created from environment configuration by `OpenAIOkHttpClient.fromEnv()`.
- Open-Meteo: daily forecast by trail coordinates and trip date.

## 3. Backend Capabilities

### User service

CURRENT and usable:

- Validate Keycloak JWTs as a stateless OAuth2 resource server.
- Return the current local profile and automatically create it from JWT claims on first access.
- Create, list, update, and soft-delete only the authenticated user's gear.
- Return structured RFC 9457/Spring `ProblemDetail` responses for user-service authentication, authorization, not-found, and DTO validation errors.

Not implemented:

- Direct registration/password endpoints. `CreateUserRequest` exists but is unused; Keycloak owns identity.
- Profile editing, preferences, favorites, saved plans, or trip history.

### Trail service

CURRENT and usable:

- Search trails by case-insensitive name substring and optional difficulty, maximum trail length, and maximum elevation gain.
- Find trails within a radius using PostGIS geography distance, ordered nearest first.
- Return a trail detail record with a GeoJSON route when route data exists.
- Enrich search and nearby summaries with scenery and baseline gear categories.

Prototype limitations:

- The dataset is not a live OpenStreetMap/Overpass import. It has two populations (planner trail-dataset change, 2026-10-17):
  - **Curated catalog:** the eight `DEMO_SEED` trails from `V2__seed_demo_trails.sql`, with `discover_visible = true` (column added by `V7__add_trail_discover_visibility.sql`, `NOT NULL DEFAULT TRUE`).
  - **Synthetic planner candidates:** 400 generated `SYNTHETIC_DEMO` trails from `V8__seed_synthetic_planner_trails.sql`, with `discover_visible = false`. They are deterministic (md5 of the row number, no `random()`; ids are `md5('synthetic-demo-trail:' || n)::uuid`), spread over eleven Southwest BC regions (303 lie within 50 km of downtown Vancouver), and exist only to make the planner's constraint space dense: 130 `EASY`, 180 `MODERATE`, 90 `HARD`, 2–28 km, 20–1,800 m gain, every scenery type, with scenery and baseline gear rows. Each description begins "Generated sample route, not a verified trail." They are not real trails.
  - `discover_visible` is catalog presentation only, not deletion, privacy, or planner eligibility. `GET /api/trails` (and so Daily Trail Activity) returns only `discover_visible` trails: it is the curated catalog, used by My Memories' trail picker. `/api/trails/nearby` and `GET /api/trails/{id}` ignore it: nearby is spatial exploration (Discover, since viewport-driven Discover) and planner candidates, so Discover shows and the planner can recommend a synthetic trail, and Trail Detail, Trip Preparation, and the Studio can open it.
- Seeded routes are all `NULL`; `TrailDetailResponse.route` is therefore currently null for demo rows.
- Cover image URLs are not populated by migrations and are currently null unless added manually.
- From FEATURE-006 (B1), `GET /api/trails`, `GET /api/trails/{uuid}`, and `GET /api/trails/activity` are public, and from viewport-driven Discover (2026-10-17) so is `GET /api/trails/nearby`, with `0 < radiusKm <= 150`. It returns only trail data already public by id; its `lat`/`lon` are a caller-supplied point, not an authenticated location. Every other trail path and method requires authentication.
- Parameter validation failures (`lat`, `lon`, `radiusKm`, `maxDistanceKm`, `maxElevationGainM`) return `400` with Spring Boot's default error body (2026-10-17: the class-level `@Validated` was removed from `TrailController`, so Spring's built-in method validation applies; before, they returned `500`). With devtools on the classpath (local IntelliJ runs) that body includes a `trace`; a deployed build must not include devtools.
- Daily Trail Activity (FEATURE-006, B2) is served by `TrailActivityService` with `SIMULATED` values: deterministic per trail and date, nothing stored, no migration. No planned-trip record exists yet, so no `RECORDED` source is possible.

### Recommendation service

CURRENT and usable:

- A temporary structured-filter endpoint for nearby trails.
- A natural-language recommendation endpoint that extracts intent with OpenAI, fetches nearby trails and owned gear, fetches per-trail weather, derives required gear, scores candidates, and returns the top three.
- A stateless conversational planner endpoint that merges the latest natural-language preference delta into a client-owned planning context, asks deterministic clarification questions until the context is ready, and then invokes the same recommendation pipeline.
- A packing endpoint that compares required gear categories with the authenticated user's inventory and returns readiness percentage.
- A basic prompt-injection phrase guard before OpenAI intent extraction.

Important qualification:

- The pack flow receives baseline trail requirements through the Trail Detail contract. Focused client and Pack tests cover detail deserialization, mild weather, weather fallback, category deduplication, ownership, and readiness.
- There is no repository-level end-to-end test spanning recommendation, trail, user, OpenAI, and Open-Meteo.

### Memory service (FEATURE-008)

CURRENT and usable (backend only). Specification: `docs/features/008-memory-foundation.md`.

- A Memory is one user's record of one real trip on one trail: `trailId`, `tripDate`, `title`, optional plain-text `story`, `visibility` (`PRIVATE` default, `PUBLIC` only when the user chooses it), and 0–5 photos. No saved-trip record is needed.
- **Owner identity:** the Keycloak `sub` of the token, stored as `owner_subject`. Not user-service's `users.id`. It is never accepted from a client and never returned.
- **Owner API** (authenticated): create, list, read, edit, soft delete, and add / reorder / remove photos, only on the caller's own Memories. Another user's, a missing, and a deleted Memory all give the same `404`.
- **Public API** (no token): a trail's `PUBLIC`, non-deleted Memories, and one such Memory. `PRIVATE` and deleted Memories are filtered in the query. Public responses use separate DTOs with no author identity of any kind.
- **Trail validation:** at creation only, one tokenless `GET /api/trails/{id}` to trail-service (missing or soft-deleted → `400 TRAIL_NOT_FOUND`; unreachable → `503`). `trailId` is immutable. Owner reads make no trail call; each public read makes exactly one, and a trail that no longer exists hides its Memories publicly while the owner still sees them. Trail fields are never copied.
- **Photos:** one `multipart/form-data` part `file` per request; JPEG, PNG, or WebP input, recognised from the bytes; ≤ 10 MB; ≤ 40 MP and ≤ 12,000 px a side; at most 5 per Memory. The cover is the lowest position.
- **Sanitization (privacy):** the server decodes each upload and writes a new image from the pixels alone (JPEG → JPEG, PNG → PNG, WebP → JPEG when opaque or PNG when it has alpha), so no EXIF, GPS, XMP, or text metadata is stored. The original upload is never stored. Animated WebP is refused. JDK ImageIO plus TwelveMonkeys `imageio-webp`.
- **Storage:** `MemoryPhotoStorage` with a local-filesystem adapter (default, development only, `memory-service/.local-storage/`, git-ignored) and an S3 adapter for production (AWS SDK v2 `s3`; private bucket; no bucket exists yet). Responses carry a short-lived signed `url` (15 minutes) and `urlExpiresAt`; the database stores only object keys, which no response contains. Locally the URL is root-relative (`/api/memories/local-photos/...`, HMAC-signed, served by memory-service); with S3 it is an absolute presigned GET URL.
- **Soft delete:** a deleted Memory's row, photo rows, and stored objects are kept; normal APIs exclude it. There is no restore. Removing one photo deletes its row and its object.
- **Frontend consumers:** FEATURE-009 My Memories uses the owner API, and FEATURE-010 Community Memories uses the public API without a token, both through the `/api/memories` development proxy (sections 7, 8).
- **Not implemented:** gateway routing, moderation, author display names, GPX, AI recap, and video.

### Plan service (FEATURE-011)

CURRENT and usable. Specification: `docs/features/011-plan-foundation-finish-preparation.md` (§6–§12).

- A Plan is one user's confirmed intention to go on one trail on one date: `id`, `trailId`, `tripDate`, `status` (`READY`, the only value), `createdAt`, `updatedAt` (UTC), plus server-internal `owner_subject` (the token's `sub`, never accepted from a client, never returned, never logged) and `deleted`. No trail, weather, or gear data is stored. Upcoming / Past is derived from `tripDate` by consumers.
- **Create is idempotent** per `(owner, trailId, tripDate)` among non-deleted Plans: `201` new, `200` with the existing Plan unchanged; concurrent creates resolve to one row (insert in its own transaction with `saveAndFlush`, unique-violation caught and re-read in a fresh one). A deleted Plan does not block recreation.
- **Trail validation** at create only, after the duplicate lookup: one tokenless `GET /api/trails/{id}` (`404` → `400 TRAIL_NOT_FOUND`; anything else → `503 TRAIL_SERVICE_UNAVAILABLE`; nothing stored). Synthetic trails are valid. `tripDate` must not be before the server's today; no maximum.
- **Isolation:** every query is scoped to the owner and `deleted = false`; another user's, a deleted, and a missing Plan are the same `404 PLAN_NOT_FOUND`. All `/api/plans/**` paths require a token; there is no public Plan endpoint. PostgreSQL error detail is suppressed in logs (`logServerErrorDetail: false`) so no owner subject reaches a log.
- **Not implemented:** update (trail and date are the identity), calendar or range queries, gateway routing.

### API gateway and activity service

No frontend-usable gateway endpoints exist, and `activity-service` is still an empty shell. Daily Trail Activity is served by `trail-service` instead (FEATURE-006, MVP placement decision). Direct service URLs or frontend development proxies are required today.

## 4. API Contracts

All current endpoints require `Authorization: Bearer <Keycloak access token>`, except the four public trail reads: `GET /api/trails`, `GET /api/trails/{uuid}`, and `GET /api/trails/activity` (FEATURE-006, B1), and `GET /api/trails/nearby` (viewport-driven Discover, 2026-10-17); and the two public Memory reads added by FEATURE-008 (every Plan endpoint of FEATURE-011 requires a token): `GET /api/memories/public` and `GET /api/memories/public/{uuid}` (plus, in local storage mode only, the signed photo URLs under `/api/memories/local-photos/`). An invalid or expired bearer token is refused even on a public path, so the frontend sends none to them. `trail-service` also permits Spring's error forward (`DispatcherType.ERROR`), so an anonymous caller receives the real status, for example `400`, instead of `401`. Verified live on 2026-10-15: list `200`, detail `200`, activity `200` (`SIMULATED`, eight entries), out-of-range activity date `400`. Verified live on 2026-10-17: `/nearby` without a token `200`, `radiusKm=151` `400`, `POST /nearby` `401`.

Status meanings:

- `stable`: implemented, covered by relevant source tests, and usable within the prototype constraints.
- `incomplete`: code exists but a known contract or behavior gap affects frontend integration.
- `temporary`: transitional behavior that should not be treated as the primary product contract.
- `mock/test`: test-only; no such public endpoint exists in the current source.

### Trail service (`http://localhost:8082`)

| Method | Path | Request / parameters | Response | Auth | Owner | Status |
|---|---|---|---|---|---|---|
| GET | `/api/trails` | Optional query: `search: string`, `difficulty: string`, `maxDistanceKm: positive number`, `maxElevationGainM: non-negative integer` | `List<TrailSummaryResponse>` of the curated catalog only (non-deleted and `discover_visible`); synthetic planner candidates are never listed | Public (FEATURE-006) | `trail-service` / `TrailController` | stable; prototype dataset |
| GET | `/api/trails/activity` | Required query: `date` (`YYYY-MM-DD`, at most one day from the server's local date) | `TrailActivityResponse`; HTTP 400 with Spring's default body when the date is missing, malformed, or out of range | Public (FEATURE-006) | `trail-service` / `TrailController`, `TrailActivityService` | stable; `SIMULATED` source |
| GET | `/api/trails/nearby` | Required query: `lat [-90,90]`, `lon [-180,180]`, `0 < radiusKm <= 150`; otherwise `400` | `List<NearbyTrailResponse>`, nearest the point first, every non-deleted trail (both sources, `discover_visible` ignored) | Public (2026-10-17) | `trail-service` / `TrailController` | stable; prototype dataset |
| GET | `/api/trails/{id}` | Path UUID `id` | `TrailDetailResponse`; HTTP 404 with empty body when absent | Public for a UUID path (FEATURE-006); a non-UUID path still requires a token | `trail-service` / `TrailController` | stable; seeded route data is null |

`TrailActivityResponse` is `{ date, source: "SIMULATED" | "RECORDED", trails: [{ trailId, activityCount }] }`, with one entry per catalog trail (non-deleted and `discover_visible`, the same set as `GET /api/trails`), ordered by name, zeros included. A trail that is absent from `trails` has unknown activity, not zero. The response carries no user identity, location, timestamp other than `date`, or participant list. Switching the source to `RECORDED` later changes no field. The full contract is in `docs/features/006-public-discover-trail-activity.md` §6.2.

`difficulty` is normalized case-insensitively and must resolve to `EASY`, `MODERATE`, or `HARD`. Invalid values produce HTTP 400. Trail lists are not paginated.

`TrailDetailResponse` contains `id`, `name`, `description`, `difficulty`, `distanceKm`, `elevationGainM`, `estimatedDurationMin`, `latitude`, `longitude`, nullable `route`, `source`, nullable `coverImageUrl`, `scenery`, and `baselineGearRequirements`. The two collection fields use the same stored values and enum wire semantics as `TrailSummaryResponse`.

#### Conversational planner contract

`POST /api/planner/turn` processes exactly one conversation turn. It is stateless: the frontend owns both displayed messages and the current `PlanningContext`, and sends the context back on every turn after the first. The backend does not persist sessions or message history.

`PlannerTurnRequest` fields:

| Field | Type | Required | Validation / behavior |
|---|---|---:|---|
| `message` | string | yes | Non-blank, maximum 2000 characters |
| `context` | `PlanningContext` or null | no | Null on the first turn; otherwise the latest context returned by the backend |
| `latitude` | number | yes | `[-90, 90]` |
| `longitude` | number | yes | `[-180, 180]` |
| `tripDate` | ISO local date (`YYYY-MM-DD`) | yes | Required |
| `radiusKm` | number or null | no | Must be greater than zero when supplied; omission preserves the existing 50 km recommendation default |

`PlanningContext` fields are `difficulty: EASY | MODERATE | HARD | null`, `maxDistanceKm: positive number | null`, `maxElevationGainM: non-negative integer | null`, `maxDurationMin: positive integer | null` (the duration in minutes, read through `durationMode`), `durationMode: APPROXIMATE | MAXIMUM | MINIMUM | null` (duration polish, 2026-10-19: null only when there is no duration; optional on requests, and a context with a duration but no mode is read as `MAXIMUM`, its earlier meaning; always present in responses; the "So far" line shows "Around …" / "Up to …" / "At least …"), `preferredScenery: SceneryType[]`, and (post-freeze planner polish, 2026-10-19) `openPreferences: PlanningPreference[]` and `lastAsked: PlanningPreference | null`, where `PlanningPreference` is `DIFFICULTY | SCENERY | TRIP_LENGTH` (`TRIP_LENGTH` covers duration, distance, and elevation). The backend normalizes a null scenery list and a null `openPreferences` to empty lists (de-duplicated, in enum order) and always returns both new fields; a client may omit them (older contexts are accepted). `openPreferences` lists dimensions the user answered with no preference ("any", "no preference", "I'm flexible"…), so a null value with the dimension listed means "any", and without it means "not answered yet". `lastAsked` is the dimension the latest clarification asked about (null on a ready response). The frontend sends both back unchanged; the planner's "So far" line shows an open dimension as "Any difficulty" / "Any trip length" / "Any scenery".

`PlannerTurnResponse` fields are:

- `status`: `NEEDS_CLARIFICATION` or `READY_TO_RECOMMEND`.
- `assistantMessage`: deterministic clarification or result summary text.
- `context`: the final context produced by merging the latest message delta into the supplied context.
- `recommendations`: an array of the existing `ScoredTrailRecommendation` objects; empty while clarification is needed.

Only explicitly mentioned preferences replace prior context values; unmentioned values remain unchanged, and one message can set several fields. The extractor receives the pending question's dimension (`lastAsked`, as a fixed server-side description) and returns named open dimensions plus an internal general-flexibility flag. A dimension named as open becomes open and loses its value (an explicit empty scenery preference opens scenery); general flexibility opens only dimensions that have no value yet and clears nothing; a dimension that receives a value leaves `openPreferences`. Each dimension is asked at most once: if `lastAsked` is still unresolved after the reply, it becomes open. Difficulty is resolved when it has a value or is open; the trip group is resolved by any duration, distance, or elevation value, a non-empty scenery list, or `TRIP_LENGTH` or `SCENERY` being open. The planner is ready when both are resolved, otherwise it asks one question (difficulty first, then trip length) and sets `lastAsked`. A message that opens a dimension is acknowledged briefly ("Got it — I'll keep the difficulty open."); a dimension opened by the ask-once fallback is acknowledged as "I'll leave the difficulty open for now." Duration phrases carry a mode: "around / about / roughly N hours", a bare "N hours", "half-day" (240), "a couple of hours" (120), "a few hours" (180), "full-day" (450), and a range (midpoint) are `APPROXIMATE`; "up to / no more than / at most / under" are `MAXIMUM`; "at least / N hours or longer / more than" are `MINIMUM`; an explicit number wins over a day term; a later duration replaces value and mode; a named open `TRIP_LENGTH` clears duration, distance, elevation, and the mode. `MAXIMUM` and `MINIMUM` are hard filters (section 6), so a bounded request may return fewer than three trails. Trip date and location are the only other required inputs (request fields). Open dimensions add no constraint: recommendation, scoring, and the weather shortlist are unchanged.

An explicit difficulty is also a recommendation eligibility constraint: when the final context says `EASY`, only trails whose difficulty is `EASY` can be returned. A non-empty `preferredScenery` list is an eligibility constraint using any-match semantics: a trail must contain at least one requested scenery type. When no candidate satisfies either explicit constraint, the ready response uses the existing empty recommendation list and no-match assistant message rather than returning a contradictory trail. Empty/unset difficulty or scenery preferences preserve the prior unconstrained behavior for that field.

When ready, the endpoint converts `PlanningContext` to the existing internal `RecommendationIntent` and uses the same nearby-trail, user-gear, weather, gear-requirement, scoring, and top-three execution path as `/api/recommendations/query`. The existing endpoint and its request/response contract remain unchanged for one-shot clients.

## 6. Trail Recommendation Flow

The conversational flow is `POST /api/planner/turn`:

1. `PlannerController` accepts the authenticated `PlannerTurnRequest` and passes the bearer token to `ConversationPlannerService`.
2. The latest message passes through the same prompt guard and OpenAI extraction integration as the one-shot endpoint, but is represented as a partial `PlanningContextDelta`. Null delta fields mean unmentioned; an explicit empty scenery list can clear scenery preferences.
3. The delta is merged over the client-supplied `PlanningContext`. The merged context is the source of truth; backend chat history does not exist.
4. The deterministic readiness rule requires difficulty to be resolved (a value or open) and one useful trip-length/scenery preference or an open trip-length/scenery dimension (section 4, conversational planner contract). If it is not met, the service returns `NEEDS_CLARIFICATION`, the merged context, a deterministic question, and an empty recommendation list without calling trail, user, weather, gear, or scoring orchestration.
5. When ready, the service returns `READY_TO_RECOMMEND` and calls the same structured recommendation execution path used by `/api/recommendations/query`.

The primary CURRENT flow is `POST /api/recommendations/query`:

1. The frontend sends `RecommendationQueryRequest` with a bearer token to `RecommendationController.recommendFromQuery()` in `Project/Backend/recommendation-service/src/main/java/com/jay/outdoor/recommendation/controller/RecommendationController.java`.
2. `RecommendationService.recommendFromQuery()` in `.../service/RecommendationService.java` delegates the message to `RecommendationIntentService`.
3. `RecommendationIntentService` calls `PromptGuard` and then `OpenAiIntentExtractor`.
4. `IntentPromptBuilder` creates a hiking-only structured extraction prompt. `OpenAiIntentClientImpl` calls the OpenAI Responses API and maps structured output to `RecommendationIntent`: difficulty, maximum distance/elevation/duration, and preferred scenery.
5. The request radius is used, or defaults to 50 km. `TrailServiceClient.getNearbyTrails()` forwards the user's bearer token to `GET /api/trails/nearby` on the trail service.
6. `TrailController.getNearbyTrails()` calls `TrailService.getNearbyTrails()`, which calls `TrailRepository.findNearbyTrails()`. The native PostGIS query uses `ST_DWithin` and `ST_Distance` on geography values, excludes soft-deleted rows, and orders by user distance. Separate repository queries batch-load scenery and baseline gear requirements.
7. `UserServiceClient.getCurrentUserGear()` forwards the same bearer token to `GET /api/users/me/gear`. `GearController` -> `GearService` -> `UserService.getOrCreateUser()` resolves or creates the profile, then `GearItemRepository` returns non-deleted owned items.
8. Weather comes last and is bounded (2026-10-17). `TrailScoringService.shortlistForWeather()` first drops candidates that fail the hard rules of step 10 (difficulty, scenery, and a `MAXIMUM` or `MINIMUM` duration bound), then ranks the rest by every weather-free factor (intent, scenery, proximity, and gear readiness against the trail's baseline requirements; ties keep nearest first) and keeps the top 15 (`RecommendationService.WEATHER_SHORTLIST_SIZE`). Only those get `WeatherServiceClient.getWeather()`, one Open-Meteo `/v1/forecast` call each, sequentially, so a turn makes at most 15 weather calls however many trails are nearby. It averages the daily minimum and maximum temperatures and reads maximum precipitation probability and wind speed. A failed lookup is logged and leaves that candidate without weather (weather score 0, baseline gear only); it no longer aborts the request. Each request logs one INFO line with the nearby and shortlist counts.
9. `GearRequirementService` combines the trail's baseline requirements with weather rules: rain gear at precipitation >= 40%, warm layer at <= 5 C, wind layer at >= 30 km/h, and sun protection at >= 25 C with precipitation < 20%.
10. `TrailScoringService` first removes candidates that contradict an explicit difficulty or non-empty scenery preference, or an explicit duration bound (`MAXIMUM`: longer trails excluded; `MINIMUM`: shorter trails excluded; a trail with no duration is never excluded and gets 0 duration points; 2026-10-19 duration polish). Difficulty is an exact match; multiple scenery values use any-match semantics. It then applies the existing scores to the shortlisted candidates: intent 55 points (difficulty 20, distance 15, elevation 10, duration 10 — for an `APPROXIMATE` duration, full points within ±15 % of the target falling linearly to 0 at ±75 %; within a `MAXIMUM`/`MINIMUM` bound, full points), weather 15, gear readiness 15, scenery 10, and proximity 5. It sorts descending and returns at most three.
11. The controller returns `RecommendationResponse { recommendations }`. Each result currently contains `trail`, total `score`, and `breakdown`; it does not return the fetched weather, `distanceFromUserKm`, derived required gear, or extracted intent.

The older `POST /api/recommendations/trails` flow only fetches nearby trails and filters them by difficulty, distance, and elevation. Treat it as temporary, not the AI planning contract.

## 7. Authentication

CURRENT architecture:

- Keycloak runs locally at `http://localhost:8180`; the realm is `outdoor-trip`.
- The frontend at `Project/Frontend/` signs users in through the Keycloak public client `outdoor-web` with Authorization Code + PKCE (S256), implemented by FEATURE-002. See "Frontend authentication" below.
- User, trail, and recommendation services are stateless OAuth2 resource servers and validate JWTs against the same issuer URI.
- Every current endpoint requires authentication except the four public trail reads and the two public Memory reads (section 4). The frontend must attach the current access token as a bearer token to every other API request. FEATURE-003 added the shared function that does this, `authenticatedApiRequest()` in `services/apiClient.ts`: it obtains the token from `getAccessToken()` (below) immediately before each request, never from storage, and attaches it only to a path under `/api/` on the configured API origin; any other path is refused before a token is asked for. Its callers are the conversational planner (`POST /api/planner/turn`), from FEATURE-004 Trip Preparation (`POST /api/recommendations/pack`), and from FEATURE-005 the Gear Customization Studio, which also calls `GET` and `POST /api/users/me/gear` (`features/gear`). From FEATURE-007, My Gear (`features/gear`) also sends `PUT /api/users/me/gear/{id}` (full replacement: it always sends `name`, `category`, and the item's current `description` unchanged) and `DELETE /api/users/me/gear/{id}` (soft delete; any `2xx`, including the empty `204`, and a `404` count as removed). From FEATURE-009, My Memories (`features/memories`) sends every owner `/api/memories` request through it, including the photo upload as `multipart/form-data` with one part `file` (a `FormData` body; the browser sets the `Content-Type` and boundary, the feature never sets it). Its request layer (`features/memories/api/memoryRequest.ts`) adds a 20 s limit (60 s for an upload) and reads a failed response's `ProblemDetail` `code` and `errors[].field` best effort. `GET /api/users/me` is still not called.
- **Public trail reads (FEATURE-006).** `features/trails/api/publicRequest.ts` makes the tokenless calls: `apiRequest()` with `credentials: "omit"`, no `Authorization` header, and the same 20-second limit and outcome kinds as `tripRequest`. Every visitor, signed in or not, reads the trail list (`trailList.ts`), nearby trails (`trailNearby.ts`, Discover), Daily Trail Activity (`trailActivity.ts`), and one trail (`trailDetail.ts`, whose `TrailDetail` also carries the trailhead `position`) this way, including the authenticated Trail Detail, Trip Preparation, and the Studio. `tripRequest` stays authenticated and is used for the pack request. From FEATURE-010, the public Memory reads (`features/community-memories/api/publicMemories.ts`) go through the same `publicRequest`: no token, `credentials: "omit"`, for every visitor.
- The recommendation service forwards that same access token to the trail and user services. It does not use a service account.
- `GET /api/users/me` is the explicit profile bootstrap. Gear operations also call `getOrCreateUser`, so they bootstrap the local profile implicitly.
- User creation assumes JWT `sub` and `email`, and uses `name` with `preferred_username` as fallback for `displayName`.

Do not add application passwords or a parallel registration system. Login, logout, session refresh, and account management should stay with Keycloak unless the backend architecture changes.

### Frontend authentication (FEATURE-002)

Specification: `docs/features/002-authentication.md`. All authentication code is in `Project/Frontend/src/features/auth/`, and `authSession.ts` is the only file that imports the adapter.

- **Adapter:** `keycloak-js` 26.2.x, the one OIDC dependency. Standard flow, PKCE S256, nonce, `responseMode: fragment`, scope `openid` (the client's defaults add `email` and `profile`).
- **Configuration:** `VITE_KEYCLOAK_URL`, `VITE_KEYCLOAK_REALM`, `VITE_KEYCLOAK_CLIENT_ID`, documented in `.env.example` and set for local work in the git-ignored `.env.local`. None is a secret; the client has no secret. Missing or unusable values leave the application signed out with sign-in reported as unavailable.
- **Credentials:** entered only on Keycloak-hosted pages reached by top-level navigation. The application has no password field.
- **Tokens:** held in the adapter's memory only. Nothing token-shaped is written to web storage, a cookie, a URL, or the console. The adapter keeps short-lived callback state in `localStorage` under `kc-callback-<state>` (state, nonce, PKCE verifier; removed when the response is processed, otherwise expiring after 60 minutes).
- **Session restore after a reload:** a hidden-frame `prompt=none` check that returns to `public/silent-check-sso.html`. It never navigates the window and never shows a Keycloak page. It relies on Keycloak's cookies being sent inside a frame: that works when the application and Keycloak are the same site (as on `localhost`) and fails closed to signed-out where third-party cookies are blocked.
- **Renewal:** the access token (300 s locally) is renewed with the refresh token about 30 s before expiry, on navigation to a protected route, when the tab becomes visible, and inside `getAccessToken()`. A refused renewal ends in the `session-expired` state.
- **Token access for later features:** `getAccessToken()` exported from `@/features/auth` returns a currently valid access token or rejects with `NotAuthenticatedError`. `getAuthenticatedSubject()`, also exported from `@/features/auth`, returns the signed-in user's `sub` claim as a plain string, or `null` when there is no session or no such claim. It exists so that per-user client state is never restored for another user; it is an identifier, not a credential, and no token or other claim is exposed through it.
- **States:** `initializing`, `unauthenticated`, `redirecting`, `callback-processing`, `authenticated`, `callback-failed`, `session-expired`, `signing-out`, `signed-out`; read with `useAuth()`. Every waiting state is bounded (9 s) and every doubt resolves to signed-out.
- **Navigation to Keycloak** happens only when the user activates Sign in or Create account. A signed-out visitor on a protected route is sent to `/` with a sign-in gate, never to Keycloak.
- **Return destination:** the protected route a signed-out visitor asked for, kept in session storage for the tab, validated against the protected routes when written and when read, used once, and never taken from a URL parameter. The accepted paths, checked by one pattern in `features/auth/returnDestination.ts`, are `/home`, `/gear`, `/trails/<segment>`, from FEATURE-004 `/trails/<segment>/prepare` and `/trails/<segment>/prepare/<YYYY-MM-DD>`, from FEATURE-005 `/trails/<segment>/prepare/<YYYY-MM-DD>/pack` (the Gear Customization Studio), and from FEATURE-009 `/memories`, `/memories/new`, `/memories/<uuid>`, and `/memories/<uuid>/edit` (a separate pattern; `?trail=` on `/memories/new` is never carried). Only the pathname is kept: a query string is never part of a destination, so Trail Detail's `rec` reference does not survive a sign-in round trip, while a Trip Preparation or Studio address does, because its trail and date are both in the path. From FEATURE-006, the Discover popup's **Sign in to plan this trip** and **Create account** call `startTrailPlanning(trailId, action)` in `authBoundary.ts`. That function saves `/trails/<id>` as the destination and then begins sign-in or registration, so a successful sign-in lands on the authenticated Trail Detail. The public header's Sign in saves no destination and lands on `/home`. A failed callback clears the destination, as before. `authBoundary.ts` also tracks the surface that started an attempt (`AuthSurface`: `"page"` or `"popup"`), so that a popup action's Working, Unavailable, and F3 states appear in the popup.
- **Sign-out:** a `POST` to Keycloak's end-session endpoint with the ID token hint in the form body, returning to `/`. It clears the in-memory session, the TanStack Query cache, the pending planning prompt, and the return destination.
- **Identity shown in the layout header** comes from the ID token (`name`, then `email`, then `preferred_username`). `GET /api/users/me` is not called by this feature.
- **Tab-scoped session-storage keys** used by the application: the pending planning prompt (still read by the planner and cleared on sign-out, but no longer written by any screen since FEATURE-006 removed the public planner composer), the return destination, markers that only choose which notice the landing shows after a sign-out or an ended session, and the planner's state (FEATURE-003): one key, `outdoor-trip-companion.planner`, defined only in `features/planning/storage/plannerSession.ts`, holding one versioned JSON value (`version`: 2, `owner`, `messages`, `context`, `tripDate`, `startingPoint`, `draft`, `draftFromLanding`). `owner` is the signed-in user's Keycloak subject (`sub`), stored for ownership only (user decision, 2026-10-12): it is never displayed or logged, and no token, raw JWT, or other claim is stored. The value is read only once the current subject is known, and is discarded and removed, whole, if it does not parse, has the wrong version or shape, has no owner, or belongs to a different subject; nothing is written without an owner, so a session with no `sub` plans in memory only. It is also removed on sign-out, on session expiry (both through `registerSessionCleanup`), and on any startup that finds no session (`PlannerSessionBoundary`, mounted in `AppProviders`). FEATURE-005 adds the loadout, the gear the user has equipped per trip: one key, `outdoor-trip-companion.loadout`, defined only in `features/loadout/storage/loadoutStorage.ts`, holding one versioned JSON value (`version`: 1, `owner`, `trips`), where `trips` maps `<trail id, lower case>/<YYYY-MM-DD>` to `{ equipped: { <GearCategory wire value>: <gear item id> }, updatedAt: <epoch ms> }`. Identifiers only: no token, no other claim, and no item name or description. It follows the planner's owner rules exactly (read only once the subject is known; discarded whole on a bad parse, version, shape, or owner; nothing written without an owner), additionally drops a malformed trip or category entry while keeping the rest, removes trips whose date is before today when read, keeps at most 20 trips (oldest `updatedAt` evicted first), stores no trip with nothing equipped, and is confirmed against the current gear list before an entry counts as Equipped (an entry whose item is gone or has another category is dropped and the corrected value written back). It is removed on sign-out and session expiry (`registerSessionCleanup`) and on a startup with no session (`LoadoutSessionBoundary`, mounted in `AppProviders` beside the planner's). New Plan does not clear it. None holds a token or grants access (each value's `owner` is an identifier, not a credential), and nothing of the planner or the loadout is written to `localStorage`.

My Memories (FEATURE-009, `features/memories`, specification `docs/features/009-my-memories.md`):

- **Server state.** Queries `["memories", "mine", <subject>]` (an infinite query, page size 12) and `["memories", "detail", <subject>, <memory id>]`: no request without a subject; `staleTime` 5 minutes and `gcTime` 10 minutes because signed photo URLs expire after 15 minutes; refetch on mount and on window focus when stale; no reconnect refetch; one automatic retry only for an unavailable service. Mutations are not optimistic: the cache is set from the server's answer, then invalidated. Trail names come from the shared `["trails", "list"]` query joined on `trailId` (no request per Memory); a `trailId` the list lacks shows "Trail unavailable". The existing session cleanup (`queryClient.clear()` on sign-out and expiry) plus the subject in every key keeps one user's Memories from ever showing for another in the same browser.
- **Signed photo URLs** are presentation only: never stored, never used as keys or identifiers (photo ids are). A photo that fails to load refetches its owning query once per result, only when that result is older than 60 s; otherwise it shows "Photo couldn't be shown". No loop.
- **Create.** Exactly one `POST /api/memories` per Memory (a ref guard), then the prepared photos are uploaded one at a time in the chosen order, then at most one reorder `PUT`, then `replace` to Detail. If a photo upload fails, the page stays in a "Memory saved, N of M photos added" state with Retry and Remove; the Memory is never deleted and never posted twice. A `POST` that times out is reported as unconfirmed ("Check My Memories"), not retried automatically.
- **Photo preparation** (`features/memories/photos/preparePhoto.ts`, browser-native, not a privacy control): JPEG, PNG, or WebP only (HEIC/HEIF and others refused with a message); a 40 MB source guard; decoded with `createImageBitmap(file, { imageOrientation: "from-image" })` (image-element fallback) so orientation is applied; long edge at most 2560 px, never upscaled; JPEG 0.88 over white for opaque images, PNG only when a PNG or WebP input has real transparency; at most 10 MB after preparation; at most 5 photos per Memory. Previews are object URLs, revoked on removal and unmount. The server's re-encoding remains the metadata boundary (FEATURE-008).
- **Edit.** One `PUT` with `tripDate`, `title`, `story`, and `visibility` (never `trailId`); photo uploads, removals, and reorders persist immediately and are serialized; while any photo request runs, the photo controls wait and Save changes is disabled. The first photo is the cover; order changes by Move earlier / Move later buttons (no drag-and-drop).
- **Leaving** a Create or Edit page with unsaved changes or running uploads asks through a native dialog (`useBlocker`) and `beforeunload`; it never blocks a navigation caused by sign-out or session end.
- **Delete** is an inline two-step confirmation on Detail; `204` or `404` removes the Memory from the cache and returns to `/memories`.
- **Notices** after save, update, and delete travel only as a router-state value (`saved`, `updated`, `deleted`). FEATURE-009 writes nothing to web storage or a cookie.
- **Entry points:** the **Memories** header link (after Gear) in `TripHeader` and `HomeHeader`, and Trail Detail's quiet "Been on this trail already? **Add a memory**" link at the end of its reading column, to `/memories/new?trail=<id>` (built by `newMemoryLocation` in `features/trails/tripRoutes.ts`).

Community Memories (FEATURE-010, `features/community-memories`, specification `docs/features/010-community-memories.md`): the signed-out, read-only consumer of FEATURE-008's public Memory API, mounted by Discover. It is trail storytelling attached to a trail, not a social feature.

- **Where.** The selected trail's popup gains a Community Memories section after the sample-data line and before the auth actions (popup order: facts → Daily Trail Activity → description and scenery → sample-data line → Community Memories → Sign in to plan this trip / Create account). It shows the public count in words, at most two compact rows (thumbnail, title, trip date; no story), and **View all memories** when there is at least one; "No public memories yet." for zero; "Community memories are unavailable." with Retry on failure. A row opens that Memory's Detail directly.
- **Synthetic trails.** For a trail where `isSyntheticTrailSource()` is true the preview query is disabled (no memory-service request) and the popup has no Community section; Community URL parameters with such a trail are dropped.
- **Panel.** View all (or a preview row) opens a Community panel: at 1024px and up a non-modal `aside` docked over the map's right side (width 360 / 380 / 400 / 440 by tier, `--community-panel-width` on `section.discover[data-community-open]`, which also moves the zoom group, attribution, map states, and gesture hint clear of it); below 1024px a native `<dialog>` opened with `showModal()` as a bottom sheet. While the rail is open the popup stays mounted and placed but is hidden (`visibility: hidden`, `inert`, `data-community-hidden`), so the popup and the panel are never on screen together; Close shows it again where its anchor puts it. The panel never moves the camera. It lists the trail's public Memories (cover, title, date, the server's excerpt) 8 per page with **Show older memories**, and shows one as a read-only public Memory Detail (title, trail, date, full story with line breaks, photos with a thumbnail strip). A `404` or a Memory whose `trailId` is not the selected trail shows "This memory is no longer available."
- **URL state.** `?trail=<id>&memories=1` (panel on the list) and `?trail=<id>&memories=1&memory=<id>` (Detail). Opening the panel or a Detail pushes a history entry marked in router state as opened in-app; in-app Back, Close, and Escape go back one entry when that marker is present and otherwise remove the parameter with `replace`, so browser Back steps Detail → list → popup with no duplicate entries. Refresh and shared links restore the panel once the trail selection resolves. Invalid combinations (no `trail`, a synthetic trail, a trail that is not selected, a non-UUID `memory`) are dropped with `replace`. Selecting another trail, closing the popup, or map movement that clears the selection removes `memories` and `memory` in the same write, so no Community UI outlives its trail. Trail selection itself stays `replace`.
- **Server state.** Public keys with no subject, separate from the owner keys (`["memories", …]`, never read, written, or invalidated here): `["community-memories", "trail", <trailId>, "preview"]` (`page=0&size=2`, enabled only for a selected, non-synthetic trail), `["community-memories", "trail", <trailId>, "list"]` (infinite, 8 per page, enabled only while the panel shows the list), `["community-memories", "detail", <memoryId>]` (enabled only while that Detail shows); ids lower-cased. `staleTime` 5 minutes, `gcTime` 10 minutes, refetch on mount and focus when stale, no reconnect refetch, no polling, one automatic retry only for an unavailable service; the query's `AbortSignal` is passed to the request. Each component reads only its current key, so a late answer for an earlier trail never shows under a new one.
- **Signed photo URLs** follow FEATURE-009's `usePhotoRecovery`: a failed image (or an already expired `urlExpiresAt`) refetches its owning query once, only when that result is older than 60 s; otherwise the fallback shows. URLs are never stored or put in the address. Preview rows and list entries load only the cover, lazily; gallery photos load only in an opened Detail.
- **Request budget** (verified in Lean QA): page load, Discover activation, hovering, and panning 0; selecting a curated trail 1 (`size=2`); a synthetic trail 0; reselecting a cached trail 0; View all 1 (8 items); each Show older memories 1; opening a Detail 1; reopening a fresh Detail 0. In development, StrictMode may abort and resend a first request.
- **Isolation and privacy.** A Community failure never closes or blocks the popup, the selection, the map, or the list, and never shows a zero. Responses carry no author identity and nothing shows one; there are no owner controls (edit, delete, visibility, upload), no likes, comments, followers, or engagement figures, and no sign-in action inside the panel. PRIVATE Memories are filtered by memory-service and never appear; a hand-built Detail URL for one shows the unavailable state.
- **Accessibility.** Preview rows and list entries are native buttons; opening the panel focuses its heading, opening a Detail focuses the Memory title, Back returns focus to the entry, Close returns it to the opener (View all or the row); Escape closes the Detail first, then the panel, never the popup. The panel announces its first result and failures once through a polite status region.

The Discover queries are `["trails", "nearby", <lat to 3 dp>, <lon to 3 dp>, <radiusKm>]` (`features/trails/hooks/useNearbyTrails.ts`; no request until Discover activates; the query's `AbortSignal` is passed to the request; `keepPreviousData`, so the previous result shows while the next view loads; only the current key's data drives the screen, so an older view's late response can never replace a newer one) and `["trails", "activity", <viewer's local date>]`, each fresh for 5 minutes, with no refetch on focus or reconnect, no polling, and no request per marker or per selection. In development, React StrictMode can abort and resend the first nearby request on a direct `/#discover` or `/?trail=` load. `GET /api/trails` (`["trails", "list"]`) is read by Discover only for the trail name search below, never on load or activation. FEATURE-006 writes nothing to `localStorage`, writes no cookie, and adds no session-storage key.

**Trail name search (post-freeze Discover usability polish, 2026-10-19; not a feature).** A labelled combobox field (placeholder `Search trails...`) above the Discover list heading (`components/TrailSearchField.tsx`, `TrailSearchResults.tsx`, `search/`). It searches, locally and with no dependency, the merge by id of the curated catalog (`GET /api/trails`, mounted by `search/CatalogRequest.ts` on the field's first focus or input, then cached by the existing `["trails", "list"]` query) and the whole loaded nearby result set (not only the 50 rows); synthetic trails beyond the loaded set are never fetched. Names are trimmed, lower-cased, and whitespace-collapsed; ranking is exact, then prefix, then contains (curated first within a rank), at most 12 shown. A non-empty query replaces the area list with the results (heading "N matching trails"; `No trails match "<query>".` with Clear search when none); an open popup is hidden meanwhile and returns when the search clears. Arrow keys move `aria-activedescendant`, Enter picks, Escape clears without closing the popup. A pick writes the shared `trail` parameter, clears the query, and eases the map to the trailhead with `TrailMapApi.focusOn(lng, lat, minZoom)` at zoom at least 12 (never zooming out; instant under reduced motion); the existing settle → `/nearby` flow refreshes the area, the popup opens, and focus moves to the selected row. A trail outside the current results uses the deep-link locate stage, which now resolves on the first view that settles after the move. Typing sends no request.

Architectural rules derived from the backend:

- Organize by product feature/domain, not by generic component type.
- Keep request functions and TypeScript contracts within their owning feature, with a small shared authenticated HTTP layer.
- Use TanStack Query for server state, cache invalidation, loading/error states, and gear mutation refreshes.
- Keep selected trail/date in route/search state for the first slice because no saved-trip resource exists.
- Keep backend enum wire values canonical and map them to human-readable labels only in the UI.
- Centralize `ProblemDetail` parsing, while tolerating inconsistent/default error responses from trail and recommendation services.

## 12. Known Technical Risks

- **Prototype data:** the eight catalog trails are hardcoded `DEMO_SEED` records and the 400 planner candidates are generated `SYNTHETIC_DEMO` records (section 3). Route and cover image values are null in the migrations.
- **Synthetic trails outside the catalog:** a `SYNTHETIC_DEMO` trail appears in Discover (viewport-driven) and in planner results, but has no Daily Trail Activity (absent from the activity list, so unknown, never zero) and cannot be chosen in the My Memories trail picker, which lists the curated catalog only. Its Trail Detail does not show "Been on this trail already? Add a memory" (`isSyntheticTrailSource()` in `features/trails/content.ts`): generated trails are not verified routes and are not used for real Memories. The sample disclosure is shown by Trail Detail and the Discover popup through `isSampleTrailSource()` in `features/trails/content.ts` (both sources), and on planner cards through the description text.
- **No gateway routing:** port 8080 is not an API entry point despite the module name.
- **Browser integration gap:** CORS exists only on trail-service and only for `http://localhost:5173`; the remaining `.env.example` lacks recommendation-service configuration.
- **Query date contract:** `RecommendationQueryRequest.tripDate` is not validated as non-null/present/future. Open-Meteo also supports a limited forecast horizon, which is not checked before the external call.
- **Recommendation latency:** `/query` and the planner make at most 15 sequential Open-Meteo requests per request, after hard filtering (section 6). A failed lookup degrades that candidate only. No timeout, retry, circuit breaker, or cache is configured, so a slow provider still slows the turn. The shortlist ranks before weather, so a trail outside the weather-free top 15 cannot be lifted into the top three by good weather (weather is 15 of 100 points).
- **Weather fallback:** `/pack` catches every exception from weather and returns baseline-only results with `weatherAvailable=false`; `/query` and the planner score a candidate whose lookup failed without weather and keep ranking.
- **Incomplete exception mapping:** recommendation-service maps only unsafe prompts and user-service unavailability. A missing selected trail can surface as HTTP 500, as can unhandled weather/OpenAI/trail-client failures. Trail-service uses default Spring errors and returns an empty 404 body for detail; user-service uses custom `ProblemDetail` with `code`.
- **Missing ranking context in response:** `/query` returns score/breakdown but omits extracted intent, weather, distance from user, and derived required gear, making explanation-rich UI difficult.
- **DTO duplication:** trail summaries, nearby wrappers, gear responses, `GearCategory`, and difficulty/scenery concepts are duplicated across services. They currently mostly align but can drift without shared contract/integration tests.
- **Loose nullability:** gear category is nullable in create/update DTOs and persistence; several trail scalar DTO fields use nullable wrapper types; frontend types must reflect this.
- **JWT claim assumptions:** automatic profile creation requires a usable email and either `name` or `preferred_username`, while the database requires non-null unique email/display name. Missing claims or identity/email conflicts can fail as server errors.
- **Keycloak setup is not reproducible from source:** no realm export exists. The documented `outdoor-trip` realm and `outdoor-web` client must already be configured, with the client settings in section 7. A redirect URI, post-logout URI, or web origin that does not match exactly breaks sign-in or sign-out.
- **Session restore depends on browser cookie policy:** the hidden-frame check needs Keycloak's cookies inside a frame. A deployment that puts the application and Keycloak on different sites would lose restore-after-reload in browsers that block third-party cookies (users would sign in again; nothing is exposed).
- **No API versioning:** all paths are under `/api/...` with no version segment.
- **Memory photo URLs (FEATURE-008):** a signed photo URL issued before a Memory is made `PRIVATE` or deleted keeps working until it expires (at most 15 minutes); there is no revocation. Accepted for the MVP.
- **Retained Memory photos (FEATURE-008):** the photo objects of a soft-deleted Memory stay in storage; there is no retention or cleanup policy yet.
- **Re-encoded photos (FEATURE-008):** sanitization drops colour profiles and slightly lowers JPEG quality, and the EXIF orientation tag is gone, so FEATURE-009 applies orientation in the browser before upload.
- **Memory storage in production (FEATURE-008):** the S3 adapter is tested offline only; no bucket, IAM role, or gateway route to memory-service exists. The local-filesystem adapter is for development only.
- **No Memory moderation (FEATURE-008):** public Memories have no reporting or review.
- **Memory photo handling in the browser (FEATURE-009):** preparation depends on `createImageBitmap` orientation support (with an image-element fallback); real Safari and physical phones were not verified. Photos are re-encoded twice (browser JPEG 0.88, then the server's 0.90). In local storage mode photo URLs are root-relative, so they work only when the page and the API share an origin (the dev proxy) or memory-service's `public-base-url` is set. A photo that failed to load on fresh data shows its fallback until the next refetch or remount.
- **Memories in production (FEATURE-009, FEATURE-010):** only the development proxy exists; production routing of `/api/memories/**` (owner and public) to memory-service, the S3 bucket with absolute presigned photo URLs, and CORS remain a deployment task (FEATURE-008 L-F, FEATURE-009 §27.3, FEATURE-010 §24.3). Community Memories work locally through the proxy only.
- **Plans in production (FEATURE-011):** only the development proxy exists; production routing of `/api/plans/**` to plan-service is a deployment task (011 U6).
- **Community Memories (FEATURE-010), verified in the final Full Regression (2026-10-19, `.claude/state/final-regression.md`):** Show older memories and its failure state, the panel and Detail error states, a Memory made Private while visible, signed-URL recovery (aged result: one refetch, no loop), the 1024px rail, and the modal sheet below 1024px (after repair R4: the sheet ignores a stale `close` event, which React StrictMode's effect re-run produced on the dev server), and reduced motion. Still not verified: signed-URL expiry in a session longer than 15 minutes, a real screen reader, Safari, and phones. On a deep-linked Detail load, focus stays on the document body (focus rules cover in-app opening only).
- **Viewport-driven Discover, accepted limitations (2026-10-17, non-blocking, post-freeze polish only):**
  - A. At wide viewports (for example 1920×1080) the default view's farthest corner is beyond 150 km, so "Zoom in to explore trails in this area." shows on first sight (at 1440×900 it is 149.2 km and does not).   - B. - **Third-party map tiles (FEATURE-006):** the Discover map depends on OpenFreeMap (tiles and glyphs). If they fail, the map shows its unavailable state and the trail list keeps working.

## 13. First Frontend Vertical Slice

# 2. Product Overview

Outdoor Trip Companion is an AI-assisted outdoor trip planning product that helps users move from:

> "I want to go somewhere this weekend."

to:

> "I know where I am going, what I need to bring, and I am ready for the trip."

and, after the trip, to:

> "I have kept and shared what I experienced."

The product combines:

- public, map-first trail discovery
- aggregate Daily Trail Activity
- conversational AI trip planning
- trail recommendation
- weather-aware decision making
- packing recommendations and readiness
- a personal gear inventory
- user-controlled gear selection for a trip, visualized on a personalized real-time 3D avatar
- trip memories and sharing

The product is organized around five stages:

**Discover → Plan → Prepare → Go in real life → Remember**

| Stage | What the software does |
|---|---|
| Discover | Cinematic Hero, public trail map, synchronized trail list, Daily Trail Activity, marker-anchored trail popup with Community Memories |
| Plan | Authenticated conversational AI planner; trail recommendation and refinement |
| Prepare | Trail selection, trip date, weather, pack recommendation, packing readiness, gear inventory, the 3D Gear Studio, the equipped loadout |
| Go in real life | Nothing. The user goes outdoors. The software does not simulate, track, or accompany the trip |
| Remember | My Memories, Memory Detail, trail and community memories, sharing |

The product presents these capabilities through two clearly separated experiences:

1. **Public Discover** — the unauthenticated homepage at `/`: a cinematic Hero that sets the outdoor atmosphere and the product promise, then a Discover section with a map of real trails, a synchronized list, Daily Trail Activity, and a marker-anchored trail popup. It converts visitors to accounts when they want personalized planning.
2. **Authenticated Product** — the personalized planning and preparation product: the Authenticated Home / Plan experience (the AI planner over a pre-rendered preparation-room background), Trail Detail with trip selection, Trip Preparation, the Gear Studio with its real-time 3D avatar, Gear Inventory, and later Memories.

The experience should feel like a personalized outdoor companion rather than a traditional trail database, an enterprise dashboard, or a game.

---

# 3. Product Vision

Outdoor trip planning should feel guided, personal, and honest about real conditions.

Instead of asking users to configure many filters, the application lets them see real trails first and then describe what they want naturally. For example:

> "I want a moderate hike with mountain views this Saturday."

The system understands the request, considers trail characteristics and weather, recommends suitable options, helps the user prepare appropriate gear, and visualizes that preparation on a personalized 3D hiking avatar. The user then goes on the real trip. Afterwards the product helps them remember and share it.

The product connects:

**real trail and planning data**

with

**purposeful visual presentation**

— a map for discovery, a calm pre-rendered room for planning, and real-time 3D only where application state changes what is visible: the Gear Studio.

The product is not a hiking simulator or an outdoor game.

---

# 4. Product Principles

## 4.1 Discovery First, AI-First Planning

Public visitors first meet the product's outdoor atmosphere and promise, then see real trails. They should not need an account to understand what the product is about.

Once signed in, conversational planning is the primary planning entry point. Users should be able to plan without understanding the application's data model, trail taxonomy, or filtering system. Traditional browsing can exist, but AI planning remains a first-class authenticated experience.

---

## 4.2 Visual but Functional

Every visual experience must support a defined product purpose:

- the public Hero's pre-rendered media communicates the product's outdoor atmosphere and promise;
- the Public Discover map supports browsing and choosing real trails;
- the Authenticated Home's pre-rendered room background provides atmosphere for planning;
- real-time 3D in the Gear Studio supports personalized product functionality.

Real-time 3D is reserved for experiences where application state changes what the user sees. Today that is the Gear Studio, where equipping gear changes the avatar. A scene that is atmosphere only, with no required object-level interaction, is pre-rendered instead (section 40.5).

Where real-time visuals exist they should reflect actual application state such as:

- the selected trail and trip
- user gear
- equipped gear
- trip preparation status

---

## 4.3 User Control

AI recommendations are suggestions rather than commands.

Users retain control over:

- trail selection
- trip date
- gear selection
- what to wear
- what to carry
- whether to accept or ignore recommendations

A recommended item must not automatically become an equipped item.

---

## 4.4 Progressive Experience

Do not present the entire application at once.

The product should progressively guide the user through:

**Discover → Plan → Choose → Prepare**

Each stage should reveal only the information needed for the current decision.

---

## 4.5 Consumer Product, Not Dashboard

The product should feel like a modern outdoor consumer application.

Avoid making the primary experience resemble:

- enterprise administration software
- a developer dashboard
- a generic AI SaaS product
- a collection of disconnected forms

---

## 4.6 3D as Product Experience, Not Core Business Logic

3D is a presentation and interaction layer for preparation.

The core product value remains:

- trail discovery
- recommendation quality
- weather-aware planning
- packing recommendations
- user gear management
- personalization

3D must enhance these capabilities rather than replace them.

---

## 4.7 Real Trails at the Door, Personalized Product Inside

The public experience earns interest by showing real trails and how much trip planning surrounds them today. After authentication, the experience shifts to personalized planning, preparation, and utility.

In product terms:

**Public Discover shows where one could go.**

**The authenticated product helps the user plan and prepare for that trip.**

The transition between these experiences should feel coherent — same brand, typography, color philosophy, and outdoor identity — but their responsibilities must remain distinct.

---

## 4.8 Honest Real-World Data

The product prepares people for real outdoor trips, so it must not overstate what it knows. In particular:

- activity figures are aggregate planning counts, never claims of physical presence (section 32);
- sample or simulated data is disclosed as such;
- missing data (routes, images, weather, activity) degrades gracefully and is never fabricated.

# 7. Entry and Home Experiences

## 7.1 Experience Boundary

Public Discover and the Authenticated Home are separate product experiences.

```text
Unauthenticated user at /
→ Public Discover

Authenticated user at /
→ Authenticated Home / Plan (/home)
```

The term **Public Discover** refers to the unauthenticated homepage at `/`: the cinematic Hero, then the Discover section. The term **Authenticated Home** refers to the authenticated planning space at `/home`: the AI planner presented over a pre-rendered preparation-room background (section 7.8). They must not be treated as the same screen or as interchangeable uses of "Home."

Returning authenticated users enter the Authenticated Home directly and do not pass through Public Discover.

The term **Public Landing** refers to the FEATURE-001 cinematic page that `/` showed before 2026-10-14, with its public planner prompt. It is historical. Its cinematic Hero, without the planner prompt, is the first section of Public Discover (section 7.6).

---

## 7.2 Public Discover Experience

Unauthenticated visitors arrive at **Public Discover**. Its purpose is to convey, immediately, the outdoor atmosphere and the product's promise, and then to let the visitor explore real trails before being asked to sign in. It is brand first, discovery second: neither a map dashboard first nor an AI chatbot first.

Public Discover is one page in two stages, in this order:

```text
Fixed public header (product identity, Discover, Sign in)
        ↓
Cinematic Hero: pre-rendered outdoor scenes, slogan, one line of support copy,
"Explore trails" (scrolls to Discover)
        ↓
Discover section: trail map + synchronized trail list
        ↓
Marker-anchored trail popup for the selected trail
        ↓
"Sign in to plan this trip" (or "Create account")
```

It contains:

- a fixed public header (product identity, Discover, Sign in);
- the cinematic Hero (section 7.6), with an **Explore trails** control that moves to Discover;
- a Discover section with a short heading, an interactive trail map, and a synchronized textual trail list;
- Daily Trail Activity for each trail (section 32);
- one marker-anchored trail popup for the selected trail (section 7.3);
- the authentication notices and sign-in actions the entry page must host (for example after a protected page was closed or a session ended), shown in the Hero.

It does not contain an AI planner input, a conversation box, suggestion prompts, or a pending public planning prompt. Discover sits below the Hero; it does not replace it.

Desktop is the primary target. In the Discover section the map is the dominant visual, and a compact list sits beside it. Exact geometry belongs to the feature specification and `DESIGN_SYSTEM.md`.

The map opens on a fixed default region (Vancouver and the Lower Mainland for the current dataset). It never requests the visitor's location.

---

## 7.3 Map, List, and Trail Popup

**Map.** Each trail in the current map area appears as a marker at its trailhead. At wider views, nearby trails merge into a cluster that shows how many trails it contains; selecting a cluster zooms in until it splits. A cluster's number counts trail records only. Markers may encode a coarse activity level, but exact activity figures are read as text: no activity or people counts, people icons, heat, or moving dots are drawn on the map, and nothing on the map implies live presence. Markers are pointer shortcuts; the map is never the only way to reach a trail.

**Synchronized trail list.** The list contains the trails in the current map area, curated and generated sample trails alike, nearest the map centre first, with their count; when there are many it shows the nearest 50 and asks the visitor to zoom in for the rest (section 1.1, 2026-10-17). Moving or zooming the map updates the list once the map comes to rest. It is the precise browsing surface, the keyboard path, and the assistive-technology path. Selecting a trail in the list or on the map selects it in both. There is one selected trail at a time.

**Trail popup.** Selecting a trail, from the list or from its marker, opens one trail popup anchored beside that trail's marker. It is the signed-out visitor's trail detail, and public trail browsing stays in it. It shows the trail name, difficulty, distance, elevation gain, estimated duration, scenery, a short description, and today's Daily Trail Activity with its sample disclosure. It shows an image only when a real one exists, and discloses sample trail data when the data is sample data. For a curated trail it also shows the trail's Community Memories (section 33.3) after the sample-data disclosure and before the actions; a generated sample trail shows none. Its primary action is **Sign in to plan this trip**, with **Create account** as the secondary action. It has no **View trail** link, does not navigate to a full Trail Detail page, and has no planning controls (trip date, Choose this trail, recommendation context, packing).

**Filters.** Not required while the trail set is small. Reconsider when it grows materially (roughly 30 or more trails).

---

## 7.4 Public Access and Authentication Gate

Public visitors may:

- open Public Discover and watch the Hero;
- browse the map and the trail list;
- select trails and read them in the trail popup;
- see Daily Trail Activity;
- read a trail's PUBLIC Memories (Community Memories, section 33.3), read-only.

Public visitors may not:

- use conversational AI planning;
- choose a trip date or prepare a trip;
- access Trip Preparation, packing, or the Gear Studio;
- open the full Trail Detail page (it is authenticated);
- manage gear;
- create memories.

Authentication is asked for when the visitor wants personalized functionality, not before they can browse.

---

## 7.5 Conversion and Return to the Trail

The primary conversion point is the trail popup on Public Discover:

```text
Trail popup (signed out)
        ↓
"Sign in to plan this trip" (or "Create account")
        ↓
Authentication
        ↓
The authenticated Trail Detail for that trail (/trails/:trailId)
        ↓
Choose a date → Choose this trail → Trip Preparation
```

The trail the visitor was reading is preserved as the authentication return destination, so they land on that trail's authenticated Trail Detail. The public popup itself is not restored after sign-in. The header's Sign in, used without a trail in mind, leads to the Authenticated Home.

There is no public planning prompt and therefore no prompt to carry through authentication. If authentication is cancelled or fails, the product shows a clear recovery path and must not imply that planning occurred.

---

## 7.6 Cinematic Public Hero

Before 2026-10-14, `/` was the FEATURE-001 cinematic Public Landing: three pre-rendered CG scenes (sunny alpine lake, rainy Pacific Northwest forest, cold mountain ridge), a central planning input, and suggestion prompts. The 2026-10-14 decision retired it from `/`.

**Amended 2026-10-15 (FEATURE-006 revision 2).** The cinematic Hero is retained as the first section of Public Discover. It reuses the FEATURE-001 media system as it is: the three scenes, posters, rotation, a stable poster under reduced motion, and Pause / Play. It carries the slogan "Discover the trail. Prepare for the journey.", one line of support copy, and **Explore trails**, which moves to the Discover section. The planning input, conversation, suggestion prompts, and any public planning prompt remain retired.

Trail discovery must not depend on the Hero media: the trail list and the map work when the video or poster is slow or fails.

---

## 7.7 Shared Art Direction

The product's pre-rendered media (the public Hero scenes and the Authenticated Home room) and its real-time 3D (the Gear Studio avatar) share an **anime-inspired stylized outdoor adventure** direction, expressed through:

- cel-shaded or stylized visual language
- painterly environments
- simplified but high-quality geometry
- natural but slightly saturated colors
- atmospheric depth
- subtle environmental motion

The direction may take inspiration from stylized Japanese adventure games, but must not reproduce copyrighted characters, proprietary environments, recognizable game UI, or specific branded assets. Product language must not characterize the experience as a clone of an existing game.

Public Discover's map follows the product's color philosophy (natural, calm, paper-like surfaces) rather than this cel-shaded style.

---

## 7.8 Authenticated Home Experience

After authentication, the Authenticated Home / Plan experience at `/home` is where AI planning happens. It is built from two layers:

1. **Background: pre-rendered looping CG/video** showing a general stylized outdoor-preparation room. The room is visual atmosphere only.
2. **Foreground: the interactive React UI**, centred on the AI planner and conversation. This is the only interactive layer.

The Authenticated Home is not a real-time 3D environment.

```text
Authenticated Home
        ↓
Pre-rendered looping room CG/video (background, atmosphere only)
        +
AI planning UI / conversation (foreground, interactive, visually central)
        ↓
AI Planning
```

### Room background

The room should visually communicate outdoor preparation. Possible visual elements include:

- entrance or gear room
- equipment shelf
- backpack
- hiking shoes
- jackets
- map
- window or outdoor view

These elements are visual direction rather than mandatory individual features. They are decorative and do not need to reflect live application state such as owned gear, equipped gear, weather, or the selected trip.

The background may show a generic character from behind, for example seated at a computer. That figure is part of the pre-rendered atmosphere. It is not the persistent avatar described in sections 16 and 17.

### Interaction

The primary interaction is AI trip planning. The planning input and conversation stay visually central and are the dominant functional UI.

The room background is not a navigation system and contains no required interactive 3D objects. The following are outside the approved scope:

- clicking the computer, the map, or gear shelves
- walking around the room, including WASD movement
- room customization
- room physics
- room inventory interaction

### Personalization

The Authenticated Home is the user's planning space. Its personalization lives in the UI layer: the conversation, planning state, and trip context.

A Home background that responds to application state, or a real-time 3D Home, is not part of the approved scope and must not be built without an explicit product decision that updates this document.

### Functional-first

The planner must be usable before the background media has loaded and when it fails to load. The background must have a reduced-motion or non-animated alternative (section 43). Temporary media, a still image, or a placeholder is acceptable.

The rationale for this architecture is recorded in section 40.5.

# 8. AI Trail Planning

The system should support natural-language requests containing combinations of:

- desired difficulty
- maximum distance
- maximum duration
- elevation preference
- scenery preference
- location

> Find an easy hike near Vancouver for tomorrow.

- distance

- scenery

## 11.3 Signed-Out Trail Popup and Authenticated Trail Detail

| | Signed out | Signed in |
|---|---|---|

| Purpose | Read about a real trail; convert when ready to plan | Choose this trail for a date |

## 13.2 Gear States

The product should distinguish between the following concepts.

### Owned

The user owns an item that belongs to the required gear category. An item is owned when it is in the user's persistent Gear Inventory (My Gear).

### Recommended

The system recommends bringing or wearing the item for this trip.

### Equipped

The user has explicitly chosen to wear or carry the item.

### Missing

The system recommends the category, but the user does not currently own an appropriate item.

These states must not be treated as equivalent.

In particular:

**Recommended ≠ Equipped**

and:

**Owned ≠ Equipped**

Canonical model (restated 2026-10-16, FEATURE-007):

| State | Meaning | Scope |
|---|---|---|
| **Owned** (My Gear / Gear Inventory) | What the user permanently owns | The user, across all trips; stored on the server |
| **Recommended** | What the trip preparation system recommends for a specific trail, date, and weather | One trip; derived, never stored on a gear item |
| **Missing** | Recommended gear not represented in the owned inventory (Recommended categories − Owned categories) | One trip; derived, never stored |
| **Equipped** | What the user selects to bring for the current trip | One trip; never a permanent property of an owned item |

**Recommended ≠ Owned ≠ Equipped.**

Examples:

- hiking boots
- trail shoes
- rain jacket
- warm layer
- backpack
- trekking poles
- headlamp
- traction
- water

The product separates two gear concepts:

| Concept | Meaning | Feature |
|---|---|---|

- A user may own multiple items in one category; one-item-per-category applies only to Equipped for a trip.
- Removing gear is a soft delete: the item stops being Owned everywhere, and a trip's Equipped selection no longer counts it.
- My Gear does not use real-time 3D. It shows category-level 2D artwork with the item's name.
- The interim category icons are the accepted shipped artwork. Replacing them with a consistent set of stylized category illustrations is visual polish (section 48), not unfinished functional scope.

# 32. Daily Trail Activity

## 32.1 Definition

**Daily Trail Activity** for trail *T* on date *D* is the number of trips planned for *T* for *D*. It is one aggregate, non-negative integer per trail per local calendar day.

User-facing wording describes planning, for example:

- "N trips planned for today"
- "1 trip planned for today"
- "No trips planned for today yet"

## 32.2 What It Is Not

Daily Trail Activity is not:

- live presence;
- GPS-derived;
- a count of people physically hiking;
- real-time;
- WebSocket presence;
- location tracking.

Copy must not imply physical presence: no "exploring today", "people on this trail", "live hikers", "currently here", "right now", or similar.

## 32.3 Source and Disclosure

The activity contract carries a source:

- **SIMULATED** — deterministic sample values generated by the backend. This is the source until a planned-trip record exists. It is disclosed to users as **Sample activity**.
- **RECORDED** — counts of real planned trips. It needs a planned-trip resource that does not yet exist. Switching from SIMULATED to RECORDED must not change the response shape.

"Activity unavailable" (for example when the request fails) is distinct from a confirmed zero and is never shown as zero. Trail discovery works fully without activity.

## 32.4 Privacy

Only aggregate counts are public. The product never exposes:

- user identity;
- participant names or lists;
- exact locations;
- timestamps tied to individuals;
- planning content.

**Superseded 2026-10-14:** the earlier Explore stage (an environment with active users, simulated live hikers, and activity indicators placed on a map) is removed.

# 33. Remember

## 33.1 Goal

Help users answer:

> What did I experience?

Remember happens after the real trip. It is delivered by FEATURE-008 (Memory Foundation), FEATURE-009 (My Memories), and FEATURE-010 (Community Memories).

My Memories (FEATURE-009, complete) is the authenticated Remember experience: the signed-in user's own journal of trips, with Memory Detail, Create, Edit, Delete, and a per-Memory Private or Public choice. Sharing back to Discover (Community Memories) is FEATURE-010 (complete, section 33.3).

---

## 33.2 Scope

Remember covers:

- **My Memories** — the user's own memories (FEATURE-009);
- **Create Memory** — recording a memory of a trip (FEATURE-009);
- **Memory Detail** — reading one memory (FEATURE-009);
- **Community Memories** on a trail's public view (the Discover trail popup, section 11.3) — memories other users have chosen to share about a trail (FEATURE-010);
- **Sharing** — making a memory visible beyond its author (the choice in FEATURE-009, the public reading in FEATURE-010).

FEATURE-008 (Memory Foundation) provides the storage, security, owner and public APIs, and private photo storage beneath both, and has no user interface. The exact inputs (for example photos and notes) and outputs are defined by `docs/features/008-memory-foundation.md` and the FEATURE-009 and FEATURE-010 specifications. Route replay from GPX, generated recap video, and other heavy pipelines are not committed.

Privacy rules: a memory is private to its author unless the author shares it; public views never reveal private planning content or individual location history beyond what the author chose to share.

## 33.3 Community Memories (FEATURE-010)

- Community Memories are **supporting evidence for a trail**: what the trail was like for people who recorded a Memory there. Discover stays trail-first.
- The selected curated trail's popup shows its PUBLIC Memories as a count, at most two short previews, and **View all memories**. View all hides the popup and opens a Community panel beside the map that lists them and opens one as a read-only public Memory; closing the panel brings the popup back (the one exception to section 41's single floating surface).
- Generated sample trails show no Community Memories, since they are not real routes.
- PUBLIC Memories are read-only for signed-out visitors (and for everyone in Discover). PRIVATE Memories never appear publicly, and a Memory that stops being public stops being shown.
- Nothing shows an author's identity. There are no likes, comments, followers, feeds, ranking, or other social features, and no creating, editing, or reporting from Discover.

## 40.4 Superseded: Adventure / Explore Environment

**Superseded 2026-10-14.** A later real-time Adventure or Explore environment is removed from the roadmap.

## 40.5 Rationale: Pre-Rendered Home (2026-10-11)

- The Authenticated Home room has no required object-level user interaction.
- A real-time 3D room would add Blender, Three.js, rendering, responsive camera, asset loading, performance, and maintenance cost without materially improving the Plan interaction.
- Pre-rendered CG/video can provide higher visual quality with substantially lower implementation complexity.
- Real-time 3D is reserved for the Gear Studio because that is where application state directly changes visible equipment on the avatar.
- This follows the principle that 3D should support product functionality rather than exist only as decoration (sections 4.2 and 4.6).

## 40.6 Rationale: Real Trips, Not Simulation (2026-10-14)

- The product's value is helping people prepare well for real trips; a simulated outdoor journey does not improve that preparation.
- Real-time outdoor scenes, walking animation, and weather effects would form a separate art and engineering project with little planning value.
- A map of real trails communicates the product to a public visitor faster and more honestly than a cinematic hero alone. (Amended 2026-10-15: the Hero is kept as the first section for atmosphere and promise, and the map follows it as the second section; section 7.6.)
- Keeping real-time 3D in the Gear Studio concentrates 3D effort where application state changes what users see.
- Ending the roadmap at Remember (FEATURE-010, amended 2026-10-16), followed by a feature freeze, protects the Capstone schedule.

# 44. Performance Principles

The product must prioritize functional usability over visual complexity.

- On Public Discover the Hero comes first: its poster and one scene's video load with the existing hero behaviour, and nothing delays the first poster. The map code, style, and tiles load only when the Discover section is about to be seen, so a visitor who stays on the Hero downloads none of them. The trail list is usable before and without the map (it then shows the default region). Discover makes one nearby-trails request when it activates, one more after each settled pan or zoom (never during the movement), and one batch activity request, with no polling and no request per marker.
- The public entry does not download authenticated planner, packing, Gear Studio, or avatar code, and loads no 3D library or model.
- The Authenticated Home's planner is usable before its background media loads and when it fails to load.
- The Gear Studio's packing and gear selection remain usable while 3D assets load, on reduced-capability devices, and when 3D is unavailable.
- 3D models and textures are optimized for web delivery, and only required assets are loaded.

# 50. Explicit Non-Goals

The following are not part of the product:

- a hiking simulation, outdoor game, or browser-based open world
- a Start Adventure action, real-time outdoor scenes, or a Home-to-Adventure transition
- walking gameplay, player-controlled movement, WASD, jumping, collision, or physics
- character combat, NPCs, or multiplayer gameplay
- complex character creation
- real-time presence, live hikers, GPS tracking, location heartbeat, background location, or WebSocket presence
- heat maps or dots representing people's locations
- automatic geolocation requests
- a public AI planner input
- making public trail discovery depend on the Hero media or any CG/video (the Hero is atmosphere; the trail list and map work without it)
- a public full Trail Detail page or a public "View trail" navigation
- a real-time 3D Authenticated Home room, or object-level interaction with that room (clicking the computer, map, or gear shelves, walking around the room, room customization, room physics, room inventory interaction)
- fully accurate recreation of every trail
- unique 3D model for every real gear SKU
- photorealistic environments
- real-time global weather simulation
- an advanced social network (followers, feeds, likes, comments) beyond the sharing of FEATURE-009 and FEATURE-010
- a full GPX/video generation pipeline
- features beyond FEATURE-014 (amended 2026-10-19; was FEATURE-010)

# 51. Product Success Criteria

The product should allow a user to complete this journey:

```text
I open the site, feel what the product is about, and see real trails near me
        ↓
I read a trail and see how much planning surrounds it today
        ↓
I sign in when I want to plan, and land on that trail's Trail Detail
        ↓
— or I describe the hike I want and receive understandable recommendations —
        ↓
I choose a trail and a date
        ↓
I understand the expected conditions
        ↓
I receive useful packing recommendations
        ↓
I compare them with gear I already own
        ↓
I equip my gear and see it on my avatar
        ↓
I feel prepared, and I go
        ↓
Afterwards I keep and share a memory of the trip
```

# 52. Primary Product Metrics

For the Capstone prototype, metrics do not need production telemetry, but product evaluation can consider:

### Discovery Comprehension

Does a signed-out visitor immediately understand that this is an outdoor trail product, and can they find and read a trail?

### Activity Comprehension

Do users understand Daily Trail Activity as trips planned, not people on the trail?

### Planning Completion

Can the user successfully move from natural-language request or a discovered trail to selecting a trail?

### Recommendation Understanding

Can the user understand why a trail was recommended?

### Packing Completion

Can the user determine what gear they need and what they already own?

### End-to-End Completion

Can the user complete:

**Discover → Plan → Prepare**

without becoming blocked?

### Visual Comprehension

Can users immediately understand that gear choices affect their avatar?

# 53. Product Risks

## Scope Expansion

3D and visual work can easily consume more time than the planning and preparation experience.

Mitigation:

Keep real-time 3D in the Gear Studio only. End the roadmap at FEATURE-010 and freeze features afterwards.

---

## Activity Misread as Presence

Visitors may read an activity number as people currently on a trail.

Mitigation:

Planning-based wording only, a sample disclosure while the source is simulated, no figures or people drawn on the map, and no location-derived data (section 32).

---

## Visual World Drift

The map-based Public Discover, the pre-rendered Home room, and the real-time Gear Studio could appear to belong to different products. The generic character in the Home room and the persistent avatar could read as unrelated characters.

Mitigation:

Shared brand, typography, color philosophy, and calm motion across all screens; shared art direction and character proportions between the Home room and the Gear Studio.

---

## Third-Party Map Tiles

The public map depends on an external tile provider.

Mitigation:

The trail list is a complete equivalent; a map failure never blocks discovery.

---

## Gear Explosion

Supporting unique models for every real-world item is not scalable for the prototype.

Mitigation:

Map many real gear items into a small set of visual categories.

---

## Backend / Frontend Contract Gaps

Some desired UI states may not yet exist in backend responses.

Mitigation:

Do not fabricate backend behavior.

Document missing requirements in `FRONTEND_CONTEXT.md` and decide whether they require:

- backend contract changes
- frontend composition
- deferred functionality

---

## Product Becoming a Game

Interactive visuals may distract from the planning purpose.

Mitigation:

No gameplay mechanics and no simulated outdoor journey (section 50).

# 54. Development Strategy

Frontend development should use incremental vertical slices.

Do not ask an AI coding agent to generate the entire frontend in one task.

Preferred workflow:

```text
Understand requirement
        ↓
Specify the feature
        ↓
Close backend contract gaps
        ↓
Implement
        ↓
Validate behavior
        ↓
Commit
        ↓
Continue to next feature
```

Pre-rendered media for the Authenticated Home may use temporary media and must not block functional work.

# 57. Agent Change Rules

AI coding agents must not reinterpret major product requirements without explicit instruction.

In particular, do not silently change:

- the journey Discover → Plan → Prepare → Go in real life → Remember
- Public Discover at `/` for signed-out visitors, and `/home` for signed-in users
- Public Discover as cinematic Hero first, then the Discover section (map plus synchronized trail list) as the public discovery surface
- no public planner composer; AI planning is authenticated
- signed-out trail detail in one marker-anchored trail popup; the full Trail Detail page is authenticated only
- "Sign in to plan this trip" from the popup, returning to the authenticated Trail Detail of the same trail
- Daily Trail Activity as an aggregate planning count, with sample disclosure and no presence claims
- a pre-rendered room CG/video background with the React AI planning UI for the Authenticated Home / Plan
- real-time 3D limited to the Gear Studio
- user-controlled gear selection
- Recommended vs Equipped distinction
- Gear Inventory vs Gear Studio distinction
- persistent avatar identity
- fixed visual gear category strategy
- the roadmap ending at FEATURE-014 (amended 2026-10-19 from FEATURE-010), then a feature freeze

If implementation limitations make a requirement difficult, report the limitation instead of silently replacing the experience.

## Visual Architecture Guard

Agents must read the visual architecture as:

- Public Discover = pre-rendered cinematic CG/video Hero (no planner), then an interactive 2D map + synchronized list
- Home / Plan background = pre-rendered CG/video
- Home interaction = the React UI planning experience
- Gear Studio = the product's real-time 3D avatar and gear experience

Without an explicit product decision that updates this document, agents must not:

- reintroduce a public planner prompt, conversation box, or suggestion prompts at `/`, or replace the Hero-then-Discover order
- create a public full Trail Detail page or a public "View trail" navigation
- request geolocation automatically, or show presence-like activity (live dots, heat, people icons, "exploring now")
- build a Start Adventure action, a real-time outdoor scene, walking gameplay, or any hiking simulation
- implement the Authenticated Home as a real-time 3D scene, or add a 3D library, 3D model, or 3D asset pipeline for it
- add object-level interaction to the Home room, such as clickable computers, maps, furniture, or gear, room navigation, movement, customization, physics, or inventory interaction
- make planning depend on the Home background media or on any 3D asset
- treat the generic character in the Home room background as the persistent avatar
- remove or weaken the Gear Studio requirements: persistent avatar identity, fixed visual gear categories, gear category to visual asset mapping, avatar equipment slots, Equip / Unequip behavior, Recommended ≠ Equipped, Owned ≠ Equipped, real-time visual changes when supported gear is equipped, and web-optimized 3D assets
